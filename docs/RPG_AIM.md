# RPG aim rendering through portals

The native `weapon_rpg` uses one small client aim dot at the portal trace endpoint, both before firing and while guiding a missile. The old server `env_sprite` is no longer created; retained helper sprites are removed on hotload. The client draws the same 16-unit point in ordinary and portal views. Leaving the portal path, switching weapons, hitting sky or disabling projectile/damage continuation restores the appropriate native behavior. The trace uses the damage feature at both endpoints and the existing hop limit.

The client adapter recognizes the map class and native C++ laser names. In the tested Linux client, the entity reports `10C_LaserDot` and bypasses its Lua `RenderOverride`. The adapter temporarily sets its client [NoDraw flag](https://wiki.facepunch.com/gmod/Entity:SetNoDraw) before rendering and restores it afterward, on cleanup or before the next frame. It preserves dots already hidden by another system. A separate world draw avoids relying on the entrance dot's render bounds when rendering the exit room.

Newly created dots are checked after native construction. Registration and pending callbacks are bounded to 64 entities, and a player's aim is traced once per frame regardless of the number of portal views. Cleanup invalidates pending callbacks. The native dot remains networked during the guidance owner handoff; `seamless_portals_rpg_owner` identifies its original player for the client renderer. Server missile steering and weapon behavior are retained.

`validation/rpg_aim_tests.py` contains 12 rendering cases covering remote endpoints, ordinary aim restoration, feature switches, sky/no-hit traces, dormant/hidden entities, visibility cleanup, native class aliases, deferred registration, guidance handoff, bounded work and an injected draw failure. The field RPG regression also rejects creation of a second sprite and checks restoration of the native owner. Seven additional sound cases cover missile removal outside client visibility, sound opt-out, source budgets, map cleanup, reload, multiple portal copies, entity-index reuse and preservation of other missiles and explosion tails. These use API doubles and are included in the release validator.

Native hotload testing used the existing singleplayer Sandbox session on `gm_construct`. The user confirmed the final small point before and during firing after removal of the extra server sprite. Dedicated multiplayer observers and clean startup/client delivery have not been validated for this rendering change. The native missile flight loop (`weapons/rpg/rocket1.wav`) was also observed through two portal audio emitters. Its native stop does not retire those separate emitters. The server now sends `SEAMLESS_PORTALS_RPG_SOUND_STOP` when a tracked missile is removed, and each client stops only that missile’s relayed flight sound. This works without requiring the original missile in the client PVS. Tracking is capped at 64 missiles and survives hotload. The user confirmed both the final aim rendering and that the motor sound stops with the explosion. Native smoke passed in the client, listen server and dedicated server; the dedicated session was Sandbox on `gm_flatgrass` without a second observer.

The isolated commit snapshot passed 247 offline checks, including all 19 RPG checks, and 58 normalized Lua syntax checks. The two existing sound failures, C-T42 and C-T43, remain reported. LuaLS with GLua definitions reported no diagnostics for the client aim module; existing dynamic API/type warnings remain in the server guidance and sound modules.
